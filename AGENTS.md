C06–C08, затем C09–C11 по зависимостям. C05 (списки) реализована. Не переписывать работающий auth без причины. Целевая модель — четыре роли, включая технического администратора (R03);
ADM01–ADM04 реализованы. C06–C08 реализованы; C09 реализована; C10 и D01–D03 реализованы; далее D05/D04/D06 и C11; данные nsuhw выдаются через ЛК, существующие аккаунты сохраняются,
новым будут генерироваться данные. Порядок их подтверждения/создания на внешнем сайте
не придумывать; согласовать до реализации nsuhw. Юридические заглушки не разрешают
сбор реальных ПДн. Актуальные решения — docs/DECISIONS.md.

## После утверждения архитектуры
Использовать существующий checkout: облачная задача уже изолирована, отдельный Git
worktree без запроса пользователя не нужен. Сначала проверить статус Git и сохранить
пользовательские изменения. Версии инструментов закреплены в package.json и package-lock.json.
Команды запуска и проверок — в README.md; текущие ограничения — в docs/HANDOFF.md.

Доступ проверять на сервере для каждого действия, включая Server Actions, Route
Handlers, фоновые задания и скачивания. Типы, скрытые кнопки и middleware не заменяют
авторизацию. Проверять год, площадку и владельца ресурса. Не доверять role/userId из
клиента. Изменения ролей, массовые операции и выдачу секретов журналировать без ПДн
и секретов в содержимом событий. Использовать SECURITY.md при проектировании изменений.

Для каждой задачи выполнять её критерии приёмки и релевантные проверки, сообщать
фактически выполненные проверки и ограничения. Не имитировать работающий email,
выдачу дипломов или интеграцию заглушками в отчёте о готовности. Не помещать реальные
ПДн, пароли и производственные выгрузки в Git, логи, тестовые фикстуры и сообщения.

## Ежегодное участие

Сервисы — src/lib/olympiad.ts, чтение/DTO — olympiad-view.ts, правила — olympiad-rules.ts.
Использовать серверную сессию, существующие транзакции/блокировки и revision.
Не менять площадку/профиль старой регистрации через повторный POST.
Частичный индекс текущего года, CHECK периода/формата и составной FK согласия
заданы SQL-миграциями; Prisma-схема выражает не все эти ограничения. Не удалять их
как «лишние» при будущих миграциях. Их поведение проверено tests/olympiad.test.ts.
Редактирование/отмена/перенос — отдельные C09–C11, с открытыми деталями в DECISIONS.

## Списки организаторов

Сервис списков — src/lib/registrations.ts. registrationsScope общий для строк,
COUNT и значений фильтров; использовать его и для будущего экспорта C06. Не заменять
его фильтрацией массива на клиенте и не выбирать actorId из тела запроса.
Поиск по ФИО/email идёт POST-телом, не URL. DTO разрешённых полей явный; пароли,
consentId и внутренние auth-поля не добавлять. Площадки с active=false не исключать
из списков старых регистраций. Пагинация offset с последним ключом id и лимитом 100.
Курс/вуз — снимки Participation, не текущие значения профиля. Команды добавятся в D02.

## Новое решение R03: технический администратор

Отдельная четвёртая роль согласована 7 ноября 2026. Она назначает главного организатора
и устанавливает сроки регистрации через интерфейс. Прежний запрет такой роли отменён.
ADM01–ADM04 реализованы; актуальное согласование R03 — в конце DECISIONS.md.
Не считать технического администратора автоматически имеющим доступ ко всем ПДн,
выгрузкам, внешним паролям и функциям других ролей. Сохраняется одна роль на аккаунт.
Сроки регистрации устанавливает и меняет только технический администратор.
Главный организатор после перехода не имеет этого права; вопрос закрыт пользователем.

Единственный TECHNICAL_ADMIN действует во всех годах. admin:bootstrap — только первый
аккаунт, staff:bootstrap отключена. Административные записи — src/lib/admin.ts:
TOTP, текущий пароль, лимит попыток и аудит проверяются сервисом. Не выносить пароль
только в Route Handler. Отзыв главного сохраняет роль/историю, удаляет сессии,
полномочия определяются действующими EditionStaffGrant. Автоматического повышения
студента/staff или доступа администратора к спискам участников нет.

Профиль и годовые исправления — corrections.ts. Самостоятельный редактор профиля
не меняет снимки заявок. Студент правит выбранный снимок до окончания/ручного закрытия,
главный — после с причиной/TOTP/паролем/лимитами. Причина хранится отдельно от аудита.
Новые операции должны учитывать revision профиля и участия.

C10: cancelParticipation использует ту же политику сроков/областей, что исправление.
Отмену нельзя восстанавливать; капитанская отмена удаляет команду, не чужие заявки.
Объявления и рассылки должны включать отменивших участие. C11 — только смена очной
площадки, без изменения ONSITE/REMOTE или дистанционной зоны.

D05: enqueueEmail вызывается только внутри предметной транзакции, actor из сессии,
получатели из серверной области. Outbox включает отменивших участие. Worker
проверяет актуальное назначение отправителя перед доставкой, хранит лишь фиксированные
коды ошибок, не выводит ПДн/SMTP text. Для --once/фонового запуска нужен учебный
режим; инструкции README. D06 повторяет рассылку актуальной аудитории с подтверждением.

D04: опубликованная Announcement неизменяема (включая SQL UPDATE/DELETE).
Исправление — новое объявление. Не отключать триггер ради тестов: сервисные тесты
используют свою схему, communications HTTP/Chromium — отдельную временную БД.
Публикация и outbox атомарны, отменившиеся адресаты включены.

D06: повтор MailBatch сохраняет шаблон/область, получает новый UUID и отдельное
подтверждение, заново выбирает аудиторию. Не копировать прошлые OutboxJob.
UUID повторного HTTP-запроса нельзя менять автоматически при сетевой ошибке.

C11: transfers.ts меняет только очную площадку активной заявки и revision.
Блокировки год → участие; причина отдельно, outbox/аудит в одной транзакции.
Не менять формат/зону, профиль, команду и явку; не расширять права администратора.

E00: LegacyNsuhwClaim — декларация старого логина, не автоматическая привязка.
Только главный назначенного года после внешней сверки/TOTP/пароля подтверждает её.
Будущая генерация E04 обязана под блокировкой User вызвать assertNoLegacyNsuhwClaim
в своей транзакции: и pending, и approved блокируют замену старого аккаунта.
Не собирать старые пароли, не связывать по ФИО, не нормализовать регистр логина
без правил nsuhw. Отказ/исправление/отзыв/перепривязка ещё не согласованы.

E04a: NsuhwLoginName — только отдельные компоненты будущего логина, не официальное
ФИО и не выданный аккаунт. Не транслитерировать/не парсить свободное ФИО молча.
Preview не проверяет занятость и не резервирует имя. E04 обязана назначить уникальный
финальный логин отдельно и заморозить его при последующих правках профиля/имён.
User-lock общий с подачей legacy-заявки: при любой legacy-заявке новые поля не менять.

E01: внешние пароли — только envelope AES-256-GCM, отдельный DEK и KEK; AAD включает
аккаунт/владельца/логин/credentialVersion, не год. Не использовать BETTER_AUTH_SECRET.
.local/ — ключевой материал, не Git. DemoLocalKeyProtector запрещён в production;
реального KMS-backend пока нет. Не выводить plaintext/envelope/ключи в DTO/логи.
PreparedExternalAccount — кандидат, не активный аккаунт nsuhw. Namespace-lock общий
с legacy (User перед namespace); не захватывать чужой User под namespace-lock.
