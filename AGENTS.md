## После утверждения архитектуры
Использовать существующий checkout: облачная задача уже изолирована, отдельный Git
worktree без запроса пользователя не нужен. Сначала проверить статус Git и сохранить
пользовательские изменения. Версии инструментов закреплены в package.json и package-lock.json.
Команды запуска и проверок — в README.md; текущие ограничения — в docs/HANDOFF.md.

Доступ проверять на сервере для каждого действия, включая Server Actions, Route
Handlers, фоновые задания и скачивания. Типы, скрытые кнопки и middleware не заменяют
авторизацию. Проверять год, площадку и владельца ресурса. Не доверять role/userId из
клиента. Изменения ролей, массовые операции и выдачу секретов журналировать без ПДн
и секретов в содержимом событий. Использовать SECURITY.md при проектировании изменений.

Для каждой задачи выполнять её критерии приёмки и релевантные проверки, сообщать
фактически выполненные проверки и ограничения. Не имитировать работающий email,
выдачу дипломов или интеграцию заглушками в отчёте о готовности. Не помещать реальные
ПДн, пароли и производственные выгрузки в Git, логи, тестовые фикстуры и сообщения.

## Ежегодное участие

Сервисы — src/lib/olympiad.ts, чтение/DTO — olympiad-view.ts, правила — olympiad-rules.ts.
Использовать серверную сессию, существующие транзакции/блокировки и revision.
Не менять площадку/профиль старой регистрации через повторный POST.
Частичный индекс текущего года, CHECK периода/формата и составной FK согласия
заданы SQL-миграциями; Prisma-схема выражает не все эти ограничения. Не удалять их
как «лишние» при будущих миграциях. Их поведение проверено tests/olympiad.test.ts.
Редактирование/отмена/перенос — отдельные C09–C11, с открытыми деталями в DECISIONS.

## Списки организаторов

Сервис списков — src/lib/registrations.ts. registrationsScope общий для строк,
COUNT и значений фильтров; использовать его и для будущего экспорта C06. Не заменять
его фильтрацией массива на клиенте и не выбирать actorId из тела запроса.
Поиск по ФИО/email идёт POST-телом, не URL. DTO разрешённых полей явный; пароли,
consentId и внутренние auth-поля не добавлять. Площадки с active=false не исключать
из списков старых регистраций. Пагинация offset с последним ключом id и лимитом 100.
Курс/вуз — снимки Participation, не текущие значения профиля. Команды добавятся в D02.

## Новое решение R03: технический администратор

Отдельная четвёртая роль согласована 7 ноября 2026. Она назначает главного организатора
и устанавливает сроки регистрации через интерфейс. Прежний запрет такой роли отменён.
ADM01–ADM04 реализованы; актуальное согласование R03 — в конце DECISIONS.md.
Не считать технического администратора автоматически имеющим доступ ко всем ПДн,
выгрузкам, внешним паролям и функциям других ролей. Сохраняется одна роль на аккаунт.
Сроки регистрации устанавливает и меняет только технический администратор.
Главный организатор после перехода не имеет этого права; вопрос закрыт пользователем.

Единственный TECHNICAL_ADMIN действует во всех годах. admin:bootstrap — только первый
аккаунт, staff:bootstrap отключена. Административные записи — src/lib/admin.ts:
TOTP, текущий пароль, лимит попыток и аудит проверяются сервисом. Не выносить пароль
только в Route Handler. Отзыв главного сохраняет роль/историю, удаляет сессии,
полномочия определяются действующими EditionStaffGrant. Автоматического повышения
студента/staff или доступа администратора к спискам участников нет.
