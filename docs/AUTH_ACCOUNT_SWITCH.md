# AUTH03 — переключение администратора и студента

Запрос пользователя от 9 ноября 2026: разные email, npm run dev / localhost:3000,
после подтверждения email студент не может войти, сообщение о ненайденном пользователе.
Пользовательская локальная БД недоступна из прикреплённой среды; в её рабочей БД
аккаунтов нет. Существующие данные/пароли/сессии пользователя не изменялись.

## Воспроизведение и исправление

В отдельной временной синтетической БД обычный сценарий успешно прошёл ещё до
исправления: администратор с настоящим TOTP → выход → новая регистрация студента
через UI → реальное письмо Mailpit → OTP → вход. В БД сохранены STUDENT,
emailVerified=true, профиль и корректная credential-запись. Сама смена ролей
не удаляет студента и не меняет его пароль.

Отдельно воспроизведена ошибка автозаполнения: DOM email заполнен без React
onChange, а submit берёт пустое/старое значение React state. До исправления
browser-тест упал на несовпадении видимого и отправленного email. В AuthForm email
получил name, submit читает FormData, trim/lowercase и использует этот адрес для
регистрации/входа/OTP/восстановления. Авторизация, сессии, роли и MFA не ослаблены;
серверные ответы при неверных данных остаются общими, без перечисления аккаунтов.
Это доказанный дефект формы, но без пользовательской БД/запроса нельзя утверждать,
что именно он вызвал описанное пользователем сообщение.

После исправления прошли обычный сценарий, DOM-autofill и обратный вход
студент → администратор с настоящим TOTP. Без TOTP администратор не получает сессию;
студент не получает страницу администратора. Тест/runner работают в своей БД,
не очищая ручные аккаунты. Добавлены npm run test:account-switch и CI step.

## Локальная диагностика без изменения аккаунта

```sh
DEMO_REGISTRATION=true npm run auth:inspect -- student@example.test
```

Замените адрес на свой синтетический. Команда доступна только в локальной учебной
БД и не печатает email, пароль/хеш, токены, ключи или реквизиты подключения.
Выдаёт exists, role, emailVerified, hasLocalPassword, hasStudentProfile и признак
известного временного test-DB. Учитываются providerId=credential и правильный accountId.
Пароль/хеш не выбираются, пароль не сбрасывается и данные не исправляются автоматически.

- exists=false: проверить ту же DATABASE_URL/сервер/порт и отсутствие очистки временной БД.
- emailVerified=false: запросить новый код и подтвердить его в этой же среде.
- hasLocalPassword=false: у нового служебного аккаунта это ожидаемо до установки
  пароля через «Забыли пароль?». У студента обычная signup должна создать credential.
- Все флаги корректны: проверить ввод именно email/пароля ЛК, автозаполнение,
  свежую work, лимит 429; при необходимости использовать штатное восстановление пароля.

CLI проверен до/после регистрации и на отказах для другого домена/production.
Обычному пользователю сайта эта служебная диагностика не выдаёт новых прав.

## Проверки

Lint/typecheck, новый Chromium/HTTP/SMTP сценарий 1/1, существующий auth HTTP 6/6,
build/check:build прошли; 76 server traces без локальных секретов. После уточнения
CLI метаданных повторены lint/types и целевой сценарий. Первый запуск теста исправил
только локаторы select/password: accessible name включал текст вариантов/подсказку.
После этого воспроизведена настоящая ошибка autofill и проверено исправление.

Общие DB/files/ops/load не перезапускались: схема/предметные сервисы не менялись.
Удалённый CI этого изменения подтверждается отдельно. Только синтетические данные;
production/main/публикация среды не затрагиваются.
