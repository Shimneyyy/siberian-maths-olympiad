# ADR-006: подтверждённый email, пароль и серверная сессия

Статус: действующая политика; статически сверено с a921c09. Источники:
[auth-core.ts](../../src/lib/auth-core.ts), [auth route](../../src/app/api/auth/[...all]/route.ts),
[session.ts](../../src/lib/session.ts), [auth-form.tsx](../../src/components/auth-form.tsx).

## Решение и причины

Вход всех ролей — email и пароль ЛК после подтверждения адреса. Серверная отзывная
сессия и актуальные назначения определяют доступ. Подтверждение email — OTP;
восстановление пароля не является подтверждением адреса или выдачей внешнего пароля.
Чувствительные действия требуют нового ввода текущего пароля, лимита и аудита.

Служебные аккаунты создаются без пароля, устанавливают его через восстановление.
Назначение главного не отправляет приглашение; назначение организатора площадки
запрашивает письмо сброса через auth API. Публичная signup не выбирает роль.

Auth-форма читает email и латинские поля из FormData, поскольку browser autofill
может не вызвать React onChange. После успешного OTP нужно явно завершать локальный
verify-режим даже при текущем /login. Resend обязан проверять структурированную
ошибку, а не объявлять успех при 429/503. Эти исправления сохраняют серверные права.

Signup готовит аккаунт и данные nsuhw транзакционно. Keyring failure откатывает
аккаунт; SMTP failure после commit оставляет его и требует повторного запроса OTP.
UI различает эти случаи фиксированными публичными кодами без исключений/секретов.
Native Windows keyring закрыт; используется WSL с сохранением прежних ключей/БД.

## Последствия

Не переносить email/секреты между шагами через URL/storage. Смена пользователя в
одном browser profile требует logout; отдельные вкладки разделяют cookies.
Проверять реальные письма Mailpit, подтверждение БД, HTTP и UI-переходы в disposable
среде. Readonly диагностика — auth:inspect, без печати хеша/пароля или исправления БД.
