# ADR-007: последовательные запросы транзакционного соединения

Статус: реализовано; статически сверено с a921c09. Решение AUDIT02, код исправления
215f7b1. [Адаптер](../../src/lib/pg-adapter.ts), [регрессия](../../tests/pg-adapter.test.ts),
[историческое расследование](../archive/investigations/BUGFIX_HISTORY.md).

## Причина

Prisma relation loader может подавать параллельные queryRaw внутри одного ORM-вызова,
даже если прикладные вызовы идут с await. Транзакция владеет одним pg connection;
параллельная подача использовала устаревающую внутреннюю очередь pg.
Последовательные await только в сервисе проблему не устраняют.

## Решение

Общая фабрика PrismaPg через публичные интерфейсы оборачивает startTransaction.
queryRaw/executeRaw выстраиваются в очередь на транзакцию. commit/rollback также
ждут ранее поданных операций до возврата соединения в пул. Ошибка отклоняет своего
вызывающего, но не оставляет очередь/rollback заблокированными. Разные транзакции
и соединения параллельны, глобальной очереди приложения нет.

App, CLI, seed и tests импортируют src/lib/pg-adapter.ts. Не патчить node_modules,
не скрывать предупреждения и не увеличивать тайм-ауты вместо исправления.
App-пул и бюджеты соединений — отдельная конфигурация, не свойство очереди.

## Последствия и проверки

Нужны негативный тест на исходном адаптере, параллельные запросы одного соединения,
rollback после SQL-ошибки и независимость разных соединений. npm run test:pg использует
--throw-deprecation; при изменении адаптера также проверять live/load и серверные scopes.
Исторические результаты не являются новым запуском этих наборов в документационной задаче.
