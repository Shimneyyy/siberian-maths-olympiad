# Полная учебная проверка сайта

Только вымышленные данные и email @example.test. Работать в существующем checkout
ветки work1. Не выполнять migrate reset, не удалять .env/.local/keyring/БД для
переключения ролей. Production и настоящие ПДн не разрешены.

## Подготовка

Остановите текущий dev-сервер. Если зависимости ещё не установлены — npm ci.
Проверьте .env: DEMO_REGISTRATION="true", BETTER_AUTH_URL="http://localhost:3000".
Не заменяйте существующий BETTER_AUTH_SECRET.

```sh
docker compose up -d --build --wait
npm run db:generate
npm run db:migrate
npm run db:seed
DEMO_REGISTRATION=true npm run nsuhw:keys -- init
npm run dev
```

Сайт: http://localhost:3000. Почта Mailpit: http://localhost:8025.
Используйте один origin (именно localhost:3000, как в BETTER_AUTH_URL).
Коды и ссылки берите из свежего письма нужного адресата; в Mailpit остаются старые
письма от завершённых тестов. При изменении .env перезапустите dev-сервер.

## Аккаунты и браузеры

| Адрес-пример | Назначение |
| --- | --- |
| admin@example.test | Существующий технический администратор |
| chief@example.test | Новый главный организатор |
| venue@example.test | Новый организатор площадки А |
| student1@example.test | Студент площадки А |
| student2@example.test | Студент площадки Б |

Если администратор уже есть, используйте его существующий адрес/пароль, не создавайте
второго. Только для самого первого аккаунта администратора:

```sh
npm run admin:bootstrap -- admin@example.test "Учебный администратор"
```

Роль одна на аккаунт, поэтому нужны разные email. Главного и организатора площадки
не регистрируют через публичную студенческую форму: назначают через соответствующий
кабинет. Уже существующий студент не повышается автоматически.

Для параллельной проверки — отдельные профили браузера или разные браузеры. Вкладки
одного профиля делят cookies; для смены пользователя в одном профиле нажимайте «Выйти».
Окна инкогнито одного профиля тоже могут делить одну сессию.

## 1. Выпуск и главный организатор

Администратор входит, подтверждает email и открывает «Техническое администрирование».
Если нужного выпуска нет, заполняет «Создать выпуск олимпиады»: год, название,
текущий пароль и подтверждение. После создания появляются сроки и назначения.
Попытка создать тот же год заново должна дать конфликт, сохранив настройки.
CLI edition:create остаётся дополнительным инструментом оператора.

Затем администратор:

1. Выбирает учебный выпуск, задаёт период, включающий текущий момент (время Новосибирска,
   UTC+7) и сохраняет сроки. Номер учебного выпуска не требует ждать соответствующего года.
2. Назначает chief@example.test главным с текущим паролем администратора.
3. Проверяет, что назначение относится к нужному году. Списков студентов у администратора нет.

Главный запрашивает «Забыли пароль?» для своего адреса и устанавливает первый пароль
по ссылке из Mailpit. Само назначение главным не отправляет автоматическое приглашение.
Затем входит: если email ещё не подтверждён, форма предложит код из нового письма.
После подтверждения повторяет вход. Восстановление пароля само
по себе не подтверждает email.

## 2. Площадки и их организатор

Главный в «Годы и площадки» делает выпуск текущим, создаёт площадки А и Б с вымышленными
адресами. В главном кабинете, в разделе «Организаторы площадок», указывает свой текущий
пароль, имя и venue@example.test, выбирает площадку А и назначает организатора.

Организатор площадки получает в Mailpit письмо установки пароля, завершает установку,
подтверждает email и входит. Он должен видеть только назначенную площадку А.
Если письмо надо запросить заново — обычное «Забыли пароль?».

## 3. Студенты, команда и области доступа

Каждый студент самостоятельно регистрируется с новым email, своим паролем ЛК,
вымышленным ФИО, вузом/курсом и латинскими компонентами нового логина nsuhw.
Подтверждает email и входит с email/паролем ЛК. Данные nsuhw не используются для входа.

Оба выбирают одинаковые выпуск/вуз, но разные площадки. Затем:

- Главный видит обоих; организатор А — только student1; студенты — только своё участие.
- Student1 и student2 создают разные команды. Student1 приглашает student2 по точному
  email; у student2 после «Обновить команды и приглашения» видно приглашение.
- Пока student2 капитан своей команды, принять нельзя. Он подтверждает «Удалить команду»,
  не отменяя участие, и принимает сохранённое приглашение. Чужие заявки не меняются.
- Главный/организатор проверяют фильтры, сортировку и CSV; организатор не получает строк площадки Б.
- Отметка явки в одном профиле видна во втором в пределах 10 секунд. Потеря связи скрывает устаревшие строки.

Дополнительно создайте student3/student4 для дистанционных МСК/НСК: их видит главный,
но не организатор очной площадки. Для конкурентных лимитов 3 команд/5 участников
используйте автоматические сценарии, а не попытку вручную нажать одновременно.

## 4. Объявления и письма

Главный публикует общее и площадочное объявления, затем общую/персонализированную
рассылку. Во втором терминале с той же рабочей .env:

```sh
DEMO_REGISTRATION=true npm run worker
```

Для разовой доставки до 20 заданий: добавьте -- --once.
Проверьте Mailpit и видимость площадочного объявления только адресованному студенту.
Повтор рассылки требует отдельного подтверждения; паролей в письмах нет.

## 5. Данные nsuhw

Новые обычные регистрации уже имеют подготовленный кандидат. Главный открывает
«Передача аккаунтов в nsuhw», проверяет состав и скачивает синтетический CSV.
Для учебного сценария можно сознательно имитировать ручную передачу и подтвердить
выбранный batch. Это не доказательство создания настоящего аккаунта на внешнем сайте.
Ничего отправлять на реальный nsuhw для локального теста не нужно.

После учебного подтверждения студент смотрит собственные данные с повторным вводом
пароля ЛК. Показ скрывается по кнопке/времени/уходу со вкладки; другой студент доступа не имеет.

## 6. Результаты и дипломы

Для старого аккаунта участник сохраняет логин в «Аккаунт nsuhw» без проверки
организатором; он сразу подходит для импорта. Для нового сохраняется отдельное
подтверждение создания после ручной передачи. Главный выбирает год и загружает CSV:

```csv
ФИО,Курс,Вуз,Логин,Задача 1,Задача 2,Сумма баллов
Учебный участник,2,Учебный вуз,<точный логин первого студента>,5,7,12
```

Замените placeholder реальным синтетическим логином из кабинета/экспорта.
Предпросмотр и применение не публикуют данные. Опубликуйте batch отдельно,
проверьте собственный результат студента и уведомление. Затем загрузите/опубликуйте
итоговые того же участника: студент видит итоговые вместо предварительных.
История по годам доступна из профиля; необязательный последний столбец «Приз»
задаёт номинацию. ФИО/курс/вуз в preview не переписывают профиль.

Для дипломов создайте настоящие синтетические PDF и ZIP без вложенных папок.
Имена — точные логины nsuhw с .pdf. Лимиты: 10 МиБ/PDF, 50 МиБ/ZIP, до 1000 PDF.
Главный проходит проверку → назначение → отдельную публикацию. Студент скачивает
свои документы, другой студент не получает чужие. При замене старый доступен до
публикации новой версии; после неё скачивается новая. PDF/AV проверяются реально.

## 7. Закрытие, исправления, отзыв и новый год

После проверки результатов/дипломов:

1. Администратор закрывает регистрацию. Студент не может править/отменять заявку.
2. Главный организатор проверяет перенос между очными площадками того же года.
   Организатор А теряет перенесённую в Б заявку.
3. Главный отзывает организатору доступ; новый запрос списка запрещён.
4. В профиле доступны опубликованные достижения и дипломы.
5. Отмену тестируйте последней: восстановление отменённого участия не предусмотрено.
6. Для проверки истории повторите создание выпуска/назначение главного в новом году,
   подтвердите участие студентом: старые снимки/результаты и аккаунт nsuhw не переписываются.

При 429 дождитесь окончания минуты. Входы и повторные проверки пароля ограничены,
пределы не надо отключать ради ручного прогона.

## Автоматические проверки

Для полного набора используйте GitHub Actions Checks либо отдельную локальную
синтетическую DATABASE_URL с миграциями/seed/keyring и PostgreSQL, Mailpit и PDF-worker.
Не запускайте общие test:db/test:http поверх БД с вашими ручными аккаунтами:
они создают/очищают fixtures и требуют единственного тестового администратора.

test:account-switch сам создаёт и удаляет отдельную временную БД; он проверяет
один браузер: администратор → выход → UI-регистрация студента → Mailpit OTP →
вход → автозаполнение → обратный вход администратором. Нужны свободный 3100 и Chromium:

```sh
PLAYWRIGHT_CHROMIUM_EXECUTABLE=/usr/bin/chromium npm run test:account-switch
```

Если Chromium установлен через Playwright, переменную пути можно не задавать.
Полная карта автоматических наборов, prerequisites и ограничений — [TESTING](TESTING.md).
Во время browser-тестов не запускайте второй dev/build/typegen в этом checkout.
Для ручного использования всегда запускайте npm run dev на 3000, а не временный тестовый сервер.

## Справочники и отказ ручного экспорта

Главный открывает «Вузы и курсы», выбирает год своего назначения и загружает
справочники. Создать синтетический курс, переименовать и отключить с текущим паролем.
Проверить, что он исчез из новых выборов, прежняя заявка сохранила свой снимок,
а stale revision и другая роль не дают изменить запись. Физического удаления нет.

При отказе 401/403 ручного экспорта/явки список должен исчезнуть, polling прекратиться;
после восстановления прав нужна явная повторная загрузка. Проверить offline,
тайм-аут, Back после смены пользователя и видимость фокуса с клавиатуры.
Автоматический smoke форм не подменяет визуальную приёмку заказчика.
