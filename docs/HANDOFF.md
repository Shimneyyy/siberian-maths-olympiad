## Реализовано

- Next.js/React/TypeScript/Tailwind, UI-компоненты, страницы auth и защищённый кабинет.
- PostgreSQL/Prisma: четыре миграции, профиль, справочники, учебные отметки,
  выпуски, назначения по годам/площадкам и аудит. Enum роли единственный на аккаунт.
- Better Auth: scrypt, email OTP, отзывные серверные сессии, восстановление пароля,
  TOTP с зашифрованными секретом/резервными кодами. Cookie-cache выключен.
- Серверная политика проверяет роль, подтверждение email, MFA, год и площадку;
  отзыв назначения действует немедленно и удаляет сессии адресата.
- Главный организатор назначает/отзывает staff через кабинет/API, с текущим паролем,
  лимитом повторных проверок и аудитом. Новому staff письмо предлагает установить
  пароль; затем нужны подтверждение email и TOTP. Студент не может стать staff.
- Первоначальное назначение главного через повторяемую CLI, без четвёртой роли,
  без пароля в выводе и без повышения существующего студента.
- Учебная регистрация атомарно сохраняет аккаунт, профиль, учебную отметку и аудит;
  коды отправляются после commit. Роль клиента игнорируется, вуз/курс валидируются.
- JSON с ограничением размера 16 KiB, проверка Origin, no-store и no-referrer для auth,
  защитные заголовки, отключение dev-логирования запросов и аргументов.
- README, dev:setup, lockfile, CI с PostgreSQL/Mailpit и проверками ниже.
- Выпуски, сроки с ручным приоритетным закрытием, текущий выпуск и ревизии настроек.
  Создание года — повторяемая CLI без автоматических прав; начальное назначение отдельно.
- Пользовательское управление площадками года: название/адрес/аудитория/инструкции,
  активность и повторное использование постоянной площадки с независимыми данными.
- Ежегодное участие: очный выбор либо МСК/НСК, актуализация профиля и отдельный
  снимок ФИО/вуза/курса, уникальность user+год, идемпотентный повтор без смены площадки.
- Приватная история собственных регистраций; отключённые площадки остаются в ней.
- Строковые блокировки выпуска согласуют регистрацию с закрытием/отключением,
  advisory lock и частичный индекс защищают выбор текущего. SQL CHECK проверяют
  даты и формат, составные FK — год площадки и владельца согласия.
- Аудит изменения срока/флагов содержит старые/новые значения, но не произвольный
  текст или персональные данные. Устаревшие формы настроек/площадок получают конфликт.

Регистрация в production всегда запрещена. В dev требуется DEMO_REGISTRATION=true,
email @example.test и явная отметка синтетических данных. Юридической политики
и действительного согласия пока нет: LEGAL_PLACEHOLDERS.md. Для несовершеннолетних
нужна утверждённая процедура до реального сбора. Не ослаблять guard ради демонстрации.

## Как продолжать

1. Использовать текущий checkout/ветку work, проверить Git и пользовательские изменения.
   Worktree без запроса не нужен. Команды запуска и env — README.md.
2. Новая среда: npm ci, npm run dev:setup, docker compose up -d --wait,
   npm run db:generate, npm run db:migrate, npm run db:seed, npm run dev.
   Существующий непустой секрет и .env не перезаписывать.
3. C06: безопасный экспорт с registrationsScope, серверной авторизацией, нейтрализацией
   CSV injection и аудитом. Не доверять переданным браузером строкам или userId.
4. C07–C08: явка с контролем версии и обновление списка до 10 секунд.
5. C09–C11: сведения уже поданной заявки, отмена и перенос. До реализации уточнить
   эффект ручного закрытия на исправления/отмену и восстановление отменённой записи.
   Перенос требует причины/аудита/уведомления и зависит от почтовой очереди D05–D06.
   Эти возможности не реализованы повторным POST, статус CANCELLED пока не выставляется
   пользовательскими endpoint. Не считать весь этап 2 закрытым только по C01–C04.
6. При каждом предметном endpoint использовать серверную сессию и политику доступа;
   actorId не брать из тела запроса. Проверять ограничения внутри транзакции записи.
7. До nsuhw подтвердить принадлежность старого аккаунта, источник пароля, ручное
   создание нового на внешней площадке и подтверждение готовности. Сгенерированный
   пароль сам по себе не создаёт аккаунт там. Account Better Auth не переиспользовать
   под nsuhw: потребуется отдельный ExternalAccount на пользователя, не только год.
8. До результатов согласовать CSV и допустимые значения/пропуски баллов по задачам;
   формулы ранжирования не выдумывать. Публикация — отдельная операция.

После каждой части обновлять DECISIONS/TASKS/HANDOFF и отправлять изменения в Git.
Исходный PRD не изменён. Реальные ПДн, пароли, токены, .env и файлы БД в Git не включать.

## C06 — безопасный экспорт

POST /api/registrations/export и кнопка CSV выгружают все страницы выбранного
фильтра. Общие registrationsScope, предикаты и сортировки со списком применяются
на сервере в RepeatableRead до чтения. Явно выбраны ФИО/email/исторические вуз/курс,
статус/формат/площадка или дистанционная зона и дата UTC. Внутренних ID, consent/auth
и внешних паролей в CSV нет; команды отложены до D02.
CSV UTF-8/BOM/запятая/CRLF, все поля заключены в кавычки, кавычки удвоены,
начальные управляющие символы и формулы = + - @ (включая ведущие пробелы/BOM)
нейтрализованы апострофом. Файл не сохраняется на сервере. Ответ attachment/no-store/
no-referrer/nosniff; параметры поиска только POST. Аудит содержит год/площадку и
число подготовленных строк, не содержимое фильтров/ФИО/email; событие не доказывает

## C11 — перенос между очными площадками

Сервис transfers.ts и POST /api/participations/transfer принимают только ID года/
участия/целевой площадки, revision, причину, пароль и явное подтверждение.
Только главный назначенного года с TOTP; отдельной привилегии администратора нет.
Разрешена действующая очная заявка и другая активная площадка того же выпуска.
Дистанционная/отменённая заявка не переносится; формат/зону изменить нельзя.
C11 не вводит нового ограничения по дедлайну для главного: согласованное Q06
позволяет ему исправить площадку с причиной, аудитом и уведомлением.

Блокировки год → участие и проверка revision защищают параллельные изменения.
Меняются только editionVenueId/revision: профиль, снимки, вуз, команда, явка и
другие годы сохраняются. Причина хранится в ParticipationCorrection, аудит —
UUID прежней/новой площадки и записи причины, без текста. Новая миграция не нужна.
Outbox TRANSFER создаётся атомарно с переносом; при ошибке откатываются площадка,
revision, причина и аудит. Уведомление только адресату заявки, без причины/пароля.
Поля {{venue}} worker получает из актуальной заявки; старая адресация площадочных
писем прекращается действующей проверкой D05.

Страница /cabinet/transfer открывается из строки действующего очного участника
у главного. Форма требует причину, пароль и подтверждение, после успеха блокирует
повторную отправку. Повтор устаревшей команды даёт 409 без нового уведомления.

## Q02 — уточнение пользовательского сценария nsuhw

Пользователь повторно подтвердил: при первичной регистрации нового участника ЛК
генерирует логин `smc.<первая буква имени>.<фамилия><индекс при совпадении>` и
случайный пароль; эти данные затем используются на nsuhw. При ежегодном
подтверждении «Я буду участвовать в SMC <год>» прежний аккаунт сохраняется,
участник попадает в список выбранного года для работы организаторов с nsuhw.
Само ежегодное подтверждение/включение в список уже реализовано C03; автоматического
создания на nsuhw или повторной генерации данных этим уточнением не заявляется.

Не считать ранее предложенную таблицу подтверждения аккаунтов утверждённой:
пользователь описал желаемый сценарий, а не принял предложенную процедуру.
До реализации остаются два важных уточнения, направленных пользователю:
1. Генерируемый пароль отдельный для nsuhw или пользователь хочет общий пароль
   для ЛК и nsuhw? Текущий ЛК использует email/самостоятельный пароль, хранит только
   его хеш и не экспортирует его (SECURITY.md). Изменение этой модели не согласовано.
2. Имеются в виду повторные участники уже из нашего ЛК либо также старые аккаунты
   nsuhw, владельцы которых ещё не зарегистрированы в ЛК? Для второго случая
   безопасная привязка пока не определена; совпадение ФИО её не доказывает.

Транслитерация/допустимые символы, формат индекса и требования пароля nsuhw всё ещё
требуют согласования с внешней площадкой. Секреты/пароли в чат не запрашиваются.
Прикладной код и auth до этих ответов не менялись; новые тесты не требуются для
документирования уточнения. Только синтетические данные; main/публикация среды
не затрагиваются.
