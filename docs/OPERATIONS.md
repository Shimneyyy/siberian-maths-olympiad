# Учебная эксплуатация и подготовка запуска

## Границы

9 ноября 2026 пользователь разрешил завершить учебный контур и проверяемую
подготовку запуска; production остаётся заблокирован. Не публиковать среду и
не сливать work в main. Только синтетические данные и локальная почта.

Принятый жизненный цикл: аккаунты/участия не удаляются автоматически; записи
результатов (год, баллы, номинация из поля «Приз») и дипломы хранятся бессрочно.
Аудит — один год, резервные копии — 30 дней. Отзыв согласия регистрирует обращение
для ручного решения оператора и не стирает историю или результаты автоматически.
Это учебная реализация требований, не юридическое заключение: до production
оператор обязан проверить основания бессрочного хранения и обращения субъектов.

## Ежедневные проверки

- GET /api/health: 200; 503 означает недоступность БД, без публикации деталей.
- Проверить доступность локального Mailpit и возраст/число PENDING/PROCESSING/FAILED
  outbox jobs. Нельзя считать queued/SMTP-accepted гарантированной доставкой адресату.
- Проверить состояние ClamAV и актуальность базы перед реальным использованием.
  Образ учебного сканера не подтверждает свежесть production-баз.
- Проверить свободное место приватных файлов, доступность keyring и резервных копий.
  Не печатать содержимое .env, keyring, SMTP-ошибок и внешних паролей.

## Сбой почты или worker

Остановить только свой worker. Не удалять OutboxJob и не создавать вручную новую
рассылку для каждого сетевого сбоя. После восстановления SMTP запустить worker по
README: просроченные lease подхватываются, fencing не даёт старому процессу затереть
новый результат. FAILED требуют изучения фиксированного кода и решения оператора;
предметный повтор рассылки выполняется через D06 с новым подтверждением.
Доставка как минимум один раз: crash после приёма SMTP может дать дубль.

## Потеря MFA/ключа или подозрение на утечку

Резервный код позволяет войти после пароля и используется один раз. Если утрачены
все факторы, не менять twoFactorEnabled/emailVerified в SQL и не удалять секрет TOTP
ради входа. Оператор проверяет личность вне системы по утверждённой процедуре;
до её определения автоматического восстановления нет. Это блокер production,
а не основание предоставлять техническому администратору доступ ко всем аккаунтам.

BETTER_AUTH_SECRET защищает TOTP и HMAC импорта: его нельзя просто заменить.
Для KEK nsuhw использовать add-version/rewrap по README с остановленным app/worker.
Старые ключи сохранять. Потерянный keyring восстанавливают из защищённой копии,
init не исправляет потерю ключа. Утечка внешнего пароля требует ручной смены на nsuhw;
ротация KEK сама по себе не меняет этот пароль.

## Резервирование и восстановление

Согласованные цели: RPO 24 часа, RTO 8 часов. Учебный restore-drill проверяет
механизм, но не устанавливает production SLA и не доказывает наличие ежедневных
копий у ещё не выбранного провайдера.

Согласованная копия должна включать PostgreSQL (все таблицы/триггеры/миграции),
приватные файлы дипломов, версионный keyring nsuhw и BETTER_AUTH_SECRET. Ключи и БД
хранятся раздельно с ограниченным доступом; настоящие production-копии шифруются
средствами выбранного провайдера. Никогда не коммитить копии или пересылать их в чат.
Перед согласованным snapshot остановить app/worker и операции дипломов/ключей.

Восстанавливать сначала в изолированную БД и приватный каталог без доступа гостей,
восстановить точные версии ключей, проверить миграции, counts, связи владельца/года,
hash PDF и расшифровку синтетического пароля. Только после этого запускать app/worker.
Обращения субъектов после snapshot нужно повторно применить до выдачи доступа;
истечение аудита повторить, бессрочные результаты/дипломы не удалять.

## Обязательные условия перед production

| Условие | Статус / требуемое доказательство |
| --- | --- |
| Оператор ПДн, основания/тексты, несовершеннолетние | Не определены; юридические заглушки не принимаются |
| Ответственные за эксплуатацию, обращения, инциденты | Не назначены |
| Хостинг/БД/файлы/копии в РФ, договоры и обработчики | Не выбраны |
| Production-KMS, права, TLS, восстановление ключей | Не реализованы под провайдера |
| Почта/DNS/SPF/DKIM/DMARC, отказ/доставка | Не настроены для настоящего домена |
| HTTPS и доверенный proxy, лимиты IP, CDN/cache | Не приняты в целевой инфраструктуре |
| Нагрузка 5000/200 и RPO/RTO | Нужны результаты учебного drill и отдельная приёмка целевой инфраструктуры |
| Реальный импорт nsuhw и защищённый канал | Проверяет ответственный вне учебных тестов |
| Мониторинг, уведомления и аварийная процедура MFA | Требуют оператора и проверенной процедуры |
| Разрешение запуска и процедура отката | Не выдавались, публикация запрещена |

До закрытия этих условий production guard сохраняется. Никаких credentials или
документов с реальными ПДн не запрашивать в чате. Реквизиты вводятся через настройки
секретов выбранного провайдера. Публикация среды и deploy не являются частью учебной
приёмки и отдельно не разрешены.

## Откат

Перед обновлением сохранить согласованный snapshot и предыдущий commit/build.
При сбое остановить app/worker, закрыть доступ, восстановить snapshot в изолированном
контуре и проверить его до переключения. Не откатывать применённые миграции простым
checkout старого кода, не выполнять prisma migrate reset и не отключать immutable
триггеры. При несовместимости восстановить целый согласованный набор БД/файлов/ключей.
Зафиксировать допустимую потерю данных по RPO и уведомить назначенного ответственного.

## Управляемые учебные копии и CLI восстановления

Нужны доступ к локальному Docker/PostgreSQL и `DEMO_REGISTRATION=true`.
App/worker должны быть остановлены, операций записи не должно быть:

```sh
DEMO_REGISTRATION=true npm run backup:create -- --confirmed-quiesced
# План истечения, без удаления:
DEMO_REGISTRATION=true npm run backup:retention
# Удалить только проверенные управляемые копии возрастом не меньше 30 дней:
DEMO_REGISTRATION=true npm run backup:retention -- --apply
# Восстановить в НОВУЮ изолированную БД/каталог, не заменяя рабочую .env:
DEMO_REGISTRATION=true npm run backup:restore -- <UUID-копии> --confirmed-isolated
npm run test:ops
npm run test:load
```

`backup:create` проверяет только синтетические email в локальной БД. PG dump,
приватные READY-файлы всех версий (через DiplomaItem) и пакет ключей шифруются
AES-256-GCM отдельными файлами с AAD UUID/назначения. Manifest также аутентифицирован.
Каталог `.local/backups` — 0700, файлы 0600; master-key `.local/backup-key`
расположен вне каталога копий. Храните его защищённую копию отдельно. Потеря ключа
при непустом каталоге блокирует init, а не заменяется новым ключом молча.
Это учебное локальное шифрование, не production-KMS и не раздельные права ОС/KMS.

Лимиты учебного snapshot: dump до 64 МиБ, до 1000 файлов по 10 МиБ и до 128 МиБ
суммарно. Превышение блокирует создание, не делает усечённую копию. Для больших
production-объёмов нужен потоковый провайдерский backup, он не имитируется этим CLI.
Карантинные orphan-файлы без DB-метаданных в snapshot не включаются и автоматически
не удаляются. Бессрочные дипломы/ключи не подчиняются сроку удаления копий.

Restore создаёт только `smo_restore_<случайный UUID>` и приватный каталог
`.local/restores/<UUID>` с `runtime.env`, keyring и файлами. Этот env содержит секреты:
не выводить/не пересылать/не коммитить его. Рабочая БД и корневая .env не заменяются.
После проверки оператор вручную выбирает согласованный runtime-конфиг; до этого
не запускать worker и не давать доступ пользователям. Автоматического переключения,
публикации или удаления предыдущей БД нет. При ошибке свои частичные ресурсы очищаются.

Команды backup/retention не устанавливают расписание ОС. В учебной эксплуатации
оператор ежедневно создаёт согласованную копию и применяет истечение. Для
production надо назначить scheduler/оператора и доказать ежедневные копии/RPO,
отдельное хранение ключей, восстановление и истечение копий у провайдера.

## Фактические проверки 9 ноября 2026

`test:ops` — три сценария: шифрование/граница 30 дней/dry-run, запреты подмены/
путей/симлинков/неизвестных файлов/потерянного ключа, настоящее pg_dump/pg_restore
в новую БД. Restore-drill восстановил PDF байт-в-байт/hash, внешний пароль с ключом,
MFA с исходным BETTER_AUTH_SECRET, результат/номинацию и SQL guards. После snapshot
создано учебное обращение; его receipt повторно применён до выдачи доступа,
старый аудит удалён, результат/диплом сохранены. Это модель внешнего журнала:
production-журнал обращений должен переживать потерю основной БД самостоятельно.
Первичная маленькая БД восстановлена за несколько секунд; не выдавать это за RTO
реальных объёмов и целевой инфраструктуры.

Нагрузочный HTTP-тест создаёт 5000 участников и их участия в двух годах (10000
записей), две площадки, 100 организаторов и 100 студенческих активных сессий.
Три измеренных волны по 200 запросов моделируют polling с интервалом 5 секунд;
дополнительная волна проверяет явку в пределах 10 секунд, затем отзыв назначения
и сессии. Проверяются JSON/no-store, собственная история и отсутствие чужой площадки.
Сессии подготовлены напрямую как уже аутентифицированные: 200 одновременных логинов,
scrypt/TOTP, 200 браузеров и длительный soak-test здесь не проверяются.

До оптимизации p95 был 4364 мс, максимум 5367 мс — несовместимо с timeout списка 4 с.
Фасеты заменены с findMany/distinct на SQL groupBy, с прежним scope и RepeatableRead.
Повтор с настоящим 4-секундным timeout списка: 600 измеренных запросов без ошибок,
p50 1682 мс, p95 2526 мс, максимум 2892 мс. Отзыв и явка прошли. Это наблюдение
локального dev-сервера, не production SLA и не проверка максимальной нагрузки ZIP/AV.

Прежние проверки outbox/lease/SMTP-failure/rollback и KEK rotation входят в общий
DB-набор; SMTP фактически доставляется в Mailpit в communications. Сбои внешней
production-почты/KMS и SLA провайдера не проверены. Перезапуск/отзыв не обходят
предметную серверную авторизацию.

## F03 — явный бюджет пула соединений (9 ноября 2026)

CI b6d9ebd прошёл предшествующие проверки, но в оптимизированной нагрузке один
запрос списка получил 503. В публичном Prisma client задан DATABASE_POOL_MAX
(по умолчанию 20, допустимо 1–50) и maxWait интерактивной транзакции 3000 мс.
Это бюджет очереди БД; HTTP timeout списка остаётся 4000 мс. Производственный
бюджет соединений нужно согласовать на все процессы/инстансы с провайдером.

Для диагностики тестовой нагрузки допускается только фиксированный marker
SYNTHETIC_API_FAILURE:Pxxxx/UNCLASSIFIED, без SQL/message/параметров/UUID/ПДн.
Он включён только у load-runner и только для синтетического актёра; обычный stderr
сервера не пересылается. Локальные lint/typecheck и изолированный production load
прошли: 600 запросов/200 сессий, 0 ошибок, p95 2313 мс, максимум 2617 мс.
Корень прежнего 503 без diagnostic code однозначно не установлен; новый CI
проверяет итоговую конфигурацию и даст фиксированный код при повторе.
